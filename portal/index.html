What a team actually maintains

The pipeline is a dependency, not a copy.

Migrating off Azure DevOps was the moment to stop shipping every team a pipeline to own. When the platform adds a scan or rotates a registry, every consuming repo picks it up on the next run — instead of forty pull requests and a spreadsheet.

Catalogue

Every service has a name, an owner and a path.

A service that is not in the catalogue is a service nobody can page. The CI workflow fails without a valid entry, which is the cheapest guardrail in the platform and catches the most common failure of all: a repo that exists but has no owner.

Guardrails

Enforced by default, not by review board.

Branch protection is applied, not requested

Linear history, code owner review and required checks are set by the scaffolder at creation. There is no window in which a new repo is unprotected.

Production needs two approvals

Environment protection rules live in GitHub, so the gate holds regardless of what a workflow file says. Dev applies straight through.

The reviewed plan is the applied plan

Terraform plans are posted to the pull request and the same artefact is applied on merge, so what was approved and what ran are the same thing.

Tags are set by the platform

Owner, cost centre and source repo are written by the baseline module. FinOps showback and the CMDB both key off them, so they are not left to memory.

Internal ingress by default

Public exposure is an explicit variable a reviewer can see in the diff, rather than something inherited from a copied config.

Off-path services stay visible

Nothing is blocked from leaving the path. It just shows up on this page with its owner next to it, which turns out to be enough.
